# Звіт: об'єктно-орієнтована система управління бібліотечною базою книг

## 1. Мета та завдання

Метою роботи було набути практичних навичок проєктування й реалізації об'єктно-орієнтованих систем на Python з використанням метакласів, декораторів, патернів проєктування, обробки винятків, модульної організації коду та мультипоточності.

Створено систему, яка зберігає книги, авторів і читачів, дозволяє видавати та повертати книги, захищає дані від некоректного вводу та обслуговує паралельні запити. Системі відповідає програмний код у пакеті `library` із тестами, демонстраційним сценарієм і бенчмарком.

## 2. Архітектура

Система побудована як пакет із шарами, де кожен модуль відповідає за одну задачу:

```
library_system/
├── library/
│   ├── __init__.py       публічний API пакету
│   ├── exceptions.py     ієрархія власних винятків
│   ├── logging_meta.py   метаклас TrackedMeta, декоратор log_call
│   ├── validators.py     функції-валідатори, декоратор @validate, перевірка ISBN
│   ├── models.py         Entity, Author, Book, Reader
│   ├── repository.py     Repository[T]: зберігання сутностей
│   ├── factories.py      BookFactory: створення книг із зовнішніх записів
│   ├── patterns.py       EventBus (Observer), LoanPolicy та StandardPolicy (Strategy)
│   ├── services.py       LibraryService: фасад бізнес-логіки
│   └── concurrency.py    run_requests: виконання запитів у пулі потоків
├── tests/
│   ├── test_models.py        метаклас, валідація, фабрика
│   ├── test_services.py      позички, каталог, події, стратегія
│   └── test_concurrency.py   потокобезпечність
├── main.py               демонстраційний сценарій
├── benchmark.py          порівняння послідовного і паралельного виконання
└── race_demo.py          демонстрація гонки з блокуванням і без нього
```

Залежності спрямовані зверху вниз. Модуль `models` не знає про сервіси, `repository` не знає про моделі конкретних типів (він працює з будь-якими сутностями з атрибутом `id`), а `services` об'єднує все разом. Клієнтський код (у прикладі це `main.py`) звертається лише до `LibraryService` і винятків з пакету `library`. Такий поділ дає змогу замінити сховище в пам'яті на базу даних, змінивши лише `repository.py`, без переписування бізнес-логіки.

## 3. Метакласи

Метаклас `TrackedMeta` (модуль `logging_meta`) є базовим для всіх сутностей системи через клас `Entity`. Він виконує два завдання.

Перше завдання: реєстрація класів. Кожен визначений клас записується в словник `registry`, що дозволяє знайти клас за іменем під час налагодження або серіалізації.

Друге завдання: логування створення об'єктів. Метаклас перевизначає `__call__`, тобто сам процес виклику `Book(...)`. Це дає точку перехоплення на рівні створення, а не в кожному `__init__`:

```python
class TrackedMeta(type):
    def __call__(cls, *args, **kwargs):
        instance = super().__call__(*args, **kwargs)
        with TrackedMeta._lock:
            number = TrackedMeta._counters.get(cls, 0) + 1
            TrackedMeta._counters[cls] = number
        logger.info("Створено %s #%d", cls.__name__, number)
        return instance
```

Логування відбувається після успішного завершення `__init__`. Якщо валідація відхилила аргументи, об'єкт не створюється, не логується і не потрапляє в лічильник. Це перевіряє тест `test_failed_creation_is_not_counted`. Лічильники захищені блокуванням, тому їх можна безпечно оновлювати з кількох потоків.

## 4. Декоратори

Система використовує три декоратори.

Декоратор `@validate(**rules)` застосовується до `__init__` моделей і перевіряє аргументи до виконання тіла функції. Правила задаються як іменовані валідатори:

```python
@validate(title=non_empty_str, isbn=valid_isbn, year=year_in_range)
def __init__(self, title, isbn, year, author): ...
```

Декоратор використовує `inspect.signature`, щоб зіставити позиційні та іменовані аргументи з параметрами функції. Тому правило можна прив'язати до аргументу незалежно від того, як його передали. Допоміжний декоратор `optional(check)` робить перевірку необов'язковою для значення `None` (наприклад, рік народження автора).

Декоратор `@log_call` застосовується до методів `LibraryService`. Він логує бізнес-помилки (`LibraryError`) на рівні WARNING і пробрасує їх далі, не змінюючи поведінки методу. Це дає журнал відмов без дублювання `try/except` у кожному методі.

Валідатор ISBN перевіряє не лише формат, а й контрольну суму для ISBN-10 і ISBN-13. Наприклад, `978-0-306-40615-7` є коректним, а `9780306406158` відхиляється, бо контрольна цифра не збігається.

## 5. Патерни проєктування

| Патерн | Розташування | Призначення в системі |
|---|---|---|
| Repository | `repository.py` | Інкапсулює зберігання сутностей, видаючи ідентифікатори і виконуючи пошук. Сервіс не знає, як саме зберігаються дані. |
| Facade | `services.py` | `LibraryService` приховує репозиторії, політики та шину подій. Клієнт викликає `borrow_book`, а не координує три компоненти вручну. |
| Factory | `factories.py` | `BookFactory.from_record` створює книгу зі словника (рядка CSV або JSON). Тут перетворюється рік із рядка і перевіряється наявність полів. |
| Observer | `patterns.py` | `EventBus` дає змогу підписатися на події `book_borrowed` і `book_returned`. Нові реакції (email-сповіщення, журнал) додаються без зміни сервісу. |
| Strategy | `patterns.py` | `LoanPolicy` визначає, скільки книг може мати читач. `StandardPolicy` є однією з реалізацій, а інші можна підставити при створенні сервісу. |

Варто відзначити, що патерн Singleton навмисно не використано. Глобальний стан ускладнює тестування, бо дані однієї перевірки протікають в іншу. Натомість сервіс створюється як звичайний об'єкт, і кожен тест отримує власну бібліотеку.

Шина подій публікує повідомлення поза блокуванням сервісу, щоб повільний підписник не утримував блокування для всіх. Збій підписника ізольований: його помилка записується в журнал, а решта підписників і основна операція виконуються далі. Це перевіряє тест `test_failing_subscriber_is_isolated`.

## 6. Обробка винятків

Усі власні винятки успадковуються від `LibraryError`. Це дає клієнту змогу перехопити всі помилки бібліотеки одним `except LibraryError`, не ловлячи випадкові помилки Python. Конкретні типи дозволяють реагувати по-різному: `BookUnavailableError` означає, що книга зайнята, `LoanLimitError` означає перевищення ліміту, `DuplicateError` означає конфлікт унікальних даних, `NotFoundError` означає відсутній ідентифікатор. `ValidationError` одночасно наслідує `ValueError`, тож його можна перехопити і як помилку значення стандартними засобами.

Стратегія обробки помилок має три правила.

Перше правило: перевірка до зміни стану. Усі вхідні дані перевіряються до будь-якої мутації, тому невдала операція не залишає об'єкти в поганому стані.

Друге правило: відкат побічних ефектів. Метод `import_book` може створити нового автора перед тим, як книга не пройде валідацію. У такому разі автор видаляється. Тест `test_invalid_import_leaves_no_orphan_author` перевіряє, що після невдалого імпорту кількість авторів не змінюється.

Третє правило: помилка одного запиту не зупиняє інших. У паралельному виконанні `run_requests` кожен запит обгорнуто у `try/except`, а результат фіксується в `RequestResult` з полями `ok` і `error`. Так видно, який саме запит відхилено і чому, без втрати решти результатів.

## 7. Мультипоточність

### Стратегія блокувань

Сервіс використовує два рівні блокування. Операції запису (додавання, позичання, повернення, реєстрація) виконуються під спільним `_write_lock` сервісу. Це робить складні дії атомарними: перевірка «книга вільна» і позначення «книга видана» виконуються разом, інший потік не може втрутитися між ними. Кожен репозиторій має власне блокування, що захищає його внутрішній словник від одночасних змін. Читання пошуку використовують лише блокування репозиторію, тому не чекають на записи в сервісі.

Щоб перевірити, що блокування справді потрібне, побудовано демонстрацію `race_demo.py`. У ній 30 читачів одночасно намагаються взяти одну книгу. Затримка 1 мс у перевірці політики відтворює ситуацію, коли перевірка звертається до зовнішнього сховища.

| Варіант | Раундів | Раундів з помилковим результатом | Максимум успішних позичок за раунд |
|---|---|---|---|
| Без блокування запису | 20 | 20 | 15 |
| З блокуванням | 20 | 0 | 1 |

Без блокування одну книгу одночасно видавали до 15 читачам, тобто гонка даних є реальною, а не теоретичною. З блокуванням коректний результат отримано у всіх раундах.

### Пул потоків

Функція `run_requests` приймає список викликів і виконує їх через `ThreadPoolExecutor` з обмеженою кількістю робочих потоків. Результати повертаються в тому самому порядку, в якому подано запити, навіть якщо виконувалися вони в різний час. Тест `test_results_keep_submission_order` перевіряє цю властивість.

### Результати бенчмарку

Бенчмарк `benchmark.py` порівнює послідовне і паралельне виконання 400 запитів. Кожне звернення до сховища має імітовану затримку 2 мс, яка відповідає роботі з диском або мережею. Без неї операції в пам'яті виконувалися б так швидко, що виміряти ефект потоків було б неможливо.

| Операція | Послідовно, с | Паралельно (8 потоків), с | Прискорення | Успішних із 400 |
|---|---|---|---|---|
| search (пошук) | 0,923 | 0,123 | 7,51× | 400 |
| borrow (позичання) | 1,757 | 1,752 | 1,00× | 400 |

Повторний запуск дав близькі значення: пошук 7,88×, позичання 1,00×.

Результати пояснюються так. Пошук читає дані, тому потоки можуть очікувати на сховище одночасно, і прискорення близьке до кількості потоків. Позичання є записом, яке свідомо серіалізоване блокуванням, тому прискорення немає. Це не дефект, а ціна коректності: щоб гарантувати одну позичку на книгу, операції запису мають виконуватися по черзі. Для прискорення записів потрібно було б блокувати не весь сервіс, а окремі книги чи читачів (блокування на рівні сутності), але це ускладнило б код і вимагало б уникати взаємних блокувань.

Окремо варто зазначити обмеження Python через GIL. Для операцій, що здебільшого обчислюють у процесорі, потоки не дають прискорення. Тому система орієнтована на сценарії з очікуванням на зовнішні ресурси, як у бенчмарку.

Стабільність перевірено повторним запуском повного набору 20 разів. Жодного збою не зафіксовано. Оскільки гонки виявляються недетерміновано, стабільність у 20 запусках є лише необхідною, але не достатньою ознакою коректності. Тому окремо виконано `race_demo.py`, який показує ефект блокування в контрольованих умовах.

### Демонстраційний сценарій

У `main.py` виконано такі дії, і результати відповідають очікуванням.

Імпорт восьми записів дав три успішні книги і п'ять відмов: некоректний ISBN, порожня назва, рік-текст, дубль ISBN та відсутній автор. Авторів після імпорту залишилось три, тобто жоден автор з відхилених записів не лишився в системі.

Під час одночасного запиту десяти читачів до однієї книги успішною стала одна позичка, а дев'ять запитів отримали `BookUnavailableError`. Сповіщення про видачу надійшло один раз.

Читач із шістьма паралельними запитами отримав три книги, а решта три відхилені через `LoanLimitError`.

## 9. Обмеження та напрями розвитку

Система зберігає дані лише в пам'яті, тому після завершення програми дані втрачаються. Це свідомий вибір для лабораторної роботи, і його легко змінити, реалізувавши інший репозиторій з тим самим інтерфейсом.

Блокування запису є глобальним для сервісу. Це просте і коректне рішення, але воно обмежує паралельність записів, як показав бенчмарк. Для великих навантажень доцільно перейти на блокування окремих сутностей.

Система не розрізняє видання однієї книги в кількох примірниках, бо кожна книга ідентифікується ISBN і має один стан. Підтримка кількох примірників потребувала б окремої сутності `Copy`.

Перевірка унікальності e-mail і ISBN відбувається лінійним пошуком по репозиторію. Для тисяч записів варто було б додати індекси (словники за ключем).

Метаклас реєструє класи в глобальному словнику, тому в процесі з багатьма версіями модулів записи можуть перетинатися. Для застосунку з одним процесом це не є проблемою.

## 10. Висновки

Реалізовано систему з чіткою модульною структурою, в якій кожен патерн і механізм виконує окрему задачу. Метаклас прозоро логує створення об'єктів і не порушує логіку класів. Декоратори відокремлюють перевірку вхідних даних від бізнес-логіки. Патерни Repository, Facade, Factory, Observer і Strategy зменшують зв'язність між компонентами і спрощують розширення.

Мультипоточність перевірено не лише тестами, які проходять, а й експериментом, що показує: без блокування запису система видає книгу кільком читачам одночасно, а з блокуванням цієї помилки немає. Бенчмарк показав, що потоки дають близько семикратного прискорення на читанні, але не на записі, і ця різниця є прямим наслідком обраної стратегії блокувань.

## 11. Запуск

Потрібен Python 3.10 або новіший, зовнішні залежності не потрібні.

```bash
python -m unittest discover -s tests -v   # тести
python main.py                            # демонстрація
python benchmark.py                       # бенчмарк
python race_demo.py                       # гонка з блокуванням і без нього
```
